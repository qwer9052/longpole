조사 과정에서 제안하고 검토한 기능을 전부 정리한 문서입니다.
근거는 `research/` 아래 세 문서와 `docs/superpowers/specs/2026-09-12-longpole-design.md`에 있습니다.

상태 표기

| 표기 | 뜻 |
|---|---|
| v1 | 구현 계획(`docs/superpowers/plans/2026-09-12-longpole.md`)에 포함됨 |

## 1. 핵심 차별점 세 가지

이 셋이 longpole의 존재 이유입니다. 기존 도구가 하나도 못 하는 것이고, 전부 실측으로 검증했습니다.

### 1.1 캐시를 인지하는 정직한 보고 · v1

액션그래프에는 캐시 적중 필드가 없습니다. 있어 보이는 세 필드는 전부 함정입니다.

| 필드 | 콜드 | 웜 | 판별 가능 |
|---|---|---|---|
| `Cmd` / `CmdReal` | 195 / 392 | 1 / 392 | **가능** |
| `NeedBuild` | 195 | 195 | 불가 |
| `Built` | 2 | 2 | 불가 |
| `Failed` | 0 | 0 | 불가 |

원인은 `writeActionGraph()`가 두 번 호출되는데 실행 전 호출이 대부분의 필드를 고정시키기 때문입니다.

이걸 모르는 유일한 경쟁자 icio/actiongraph는 **아무것도 재빌드하지 않은 빌드에서 캐시 조회를 "가장 느린 빌드 단계"로 보고합니다.** longpole은 같은 상황에서 이렇게 말합니다.

```
build: 392 actions, 0 ran, 392 cached (100%)          0.50s wall
nothing to optimize — everything came from cache
```

### 1.2 큐 대기와 작업 시간 분리 · v1

`TimeStart - TimeReady`는 액션이 준비됐지만 스케줄되지 못한 시간입니다. 그래프에 공짜로 들어 있는데 어떤 도구도 노출하지 않습니다.

이게 왜 중요한지 보여주는 실제 사례가 있습니다. Go 이슈 #71981은 Windows 빌드가 40초 걸리고 그중 40.348초(99.17%)가 `internal/godebugs` 한 패키지에 찍힌 사건입니다. 실제 원인은 그 패키지가 아니라 툴 ID 계산의 락 경합이었습니다. **벽시계만 보는 도구는 엉뚱한 패키지를 범인으로 지목합니다.** 작업 시간, 벽시계, 큐 대기를 따로 보고하면 제대로 짚습니다.

콜드 픽스처에서 1ms 이상 대기한 액션이 47개, 최대 384ms였습니다. 실제로 나오는 신호입니다.

### 1.3 빌드 간 ActionID diff · v1

`ActionID`는 같은 머신에서 실행 간 완전히 결정적입니다. 따라서 "이 패키지가 지난 실행엔 캐시됐는데 이번엔 재빌드됨"을 정확히 말할 수 있습니다.

ActionID가 바뀌는 조건과 안 바뀌는 조건을 실측했습니다.

| 변경 | ActionID 바뀜 |
|---|---|
| 소스 내용 | 예 |
| Go 버전 | 예 (버전 문자열이 모든 해시에 소금으로 들어감) |
| `GOOS` / `GOARCH` / `GOAMD64` | 예 |
| `-trimpath` | 예 |
| `-gcflags=all=...` | 예 |
| **절대 패키지 디렉토리** | **예** |
| `-ldflags` | 아니오 (링크 전용) |
| `-tags` (파일 선택이 안 바뀌면) | 아니오 |
| `-gcflags` (`all=` 없이) | 아니오 |
| `CGO_ENABLED` (cgo 파일 없는 패키지) | 아니오 |

여기서 사용자에게 알려줄 가치가 큰 사실이 두 개 나옵니다.

- CI 체크아웃 경로가 다르면 개발자 캐시와 **아무것도 공유하지 않습니다.** `-trimpath`가 이걸 해결합니다.
- **소스를 고쳐도 의존하는 패키지가 자동으로 무효화되지 않습니다.** 패키지 해시에는 의존성의 *출력 내용* ID가 들어가므로, 출력이 같으면 하위 패키지는 캐시됩니다. 사람들이 거의 항상 오해하는 부분이라 설명 자체가 제품 가치입니다.

## 2. v1에 들어가는 기능

### 2.1 명령 구성

| 명령 | 동작 |
|---|---|
| `longpole go build ./...` | 빌드 프로파일 |
| `longpole go test ./...` | 테스트 빌드 프로파일 |
| `longpole --explain go build ./...` | 재빌드 원인까지 추적 (느림) |
| `longpole log` | 최근 실행 목록 |
| `longpole diff [A B]` | 두 실행 비교, 기본은 최근 둘 |

### 2.2 리포트에 들어가는 항목

- **시간 분배**: compile / link / vet / cache 별 작업 시간과 비율
- **크리티컬 패스**: 의존 작업의 가장 무거운 사슬과 전체 벽시계 대비 비율
- **병렬도**: 작업 시간 ÷ 벽시계, 코어 수 대비. 큐 대기가 많으면 경고
- **가장 느린 패키지**: 작업 시간 기준. 캐시된 액션은 제외
- **blast radius**: 이 패키지가 몇 개의 하위 액션을 막고 있는지
- **재빌드 근원**(`--explain`): 스스로 바뀐 패키지와 뒤따라 재빌드된 개수

### 2.3 투명성 규칙

래퍼가 빌드를 방해하면 안 된다는 원칙입니다. 이게 무너지면 아무도 안 씁니다.

- 종료 코드를 그대로 전달
- stdout, stderr 바이트 단위 통과. 리포트는 자식 종료 후 stderr로
- Ctrl-C를 자식에게 전달하고 자식이 끝날 때까지 대기 (직접 죽이면 그래프를 잃음)
- 분석이 실패해도 경고 한 줄만 남기고 종료 코드는 유지
- 사용자가 이미 `-debug-actiongraph`를 넘겼으면 그쪽을 존중
- `--explain`이 유발한 `HASH` 줄만 걸러내고 나머지 stderr는 전부 통과

### 2.4 `--explain`의 원인 추적

`GODEBUG=gocachehash=1`이 모든 캐시 해시의 입력 스트림을 순서대로 stderr에 찍습니다.

```
HASH[build example.com/lab/a]: "go1.27.1"
HASH[build example.com/lab/a]: "dir C:\\...\\lab\\a\n"
HASH[build example.com/lab/a]: "file a.go 9SqAMQcEh9zzRXLLCibe\n"
HASH[build example.com/lab/a]: "import fmt 6yHny8j1aq7yvW1BoyvM\n"
HASH[build example.com/lab/a]: 2c9680efc7e3447c...
```

두 실행의 이 블록을 비교하면 "config.go가 바뀌어서"까지 정확히 말합니다.

마지막 다이제스트는 액션그래프의 `ActionID`와 이어집니다. ActionID는 같은 SHA-256의 **앞 15바이트를 base64url로 인코딩**한 값입니다. 실측 확인: `2c9680efc7e3447c...` → `LJaA78fjRHyrIOReFVuZ`. 이 연결 덕분에 원인을 패키지와 비용에 동시에 귀속시킬 수 있습니다.

**기준선 없이도 동작하는 설계**: 패키지 해시 입력에 의존성의 출력 ID가 들어 있으므로, 한 번의 빌드 안에서도 "B는 A 때문에, A는 자기 소스 때문에"까지 사슬을 추적합니다. 기준선이 없으면 근원을 "자기 소스나 설정이 바뀜"으로 보고하고, 기준선이 쌓이면 "file config.go 바뀜"으로 승격합니다.

**비용 주의**: 4패키지 + 표준 라이브러리 모듈에서 stderr 962KB가 나옵니다. hello world 하나도 3,958줄입니다. 버퍼링 없이 스트림 파싱해야 하고 옵트인이어야 합니다.

## 3. 미룬 기능

### 3.1 GOCACHEPROG 가로채기 · v2

**무엇**: 캐시 적중/실패와 캐시 I/O 시간을 서브키까지 포함해 정확히 기록.

**검증 상태**: 동작하는 구현을 만들어 확인했습니다. 콜드 1,169 이벤트(390 get 전부 miss, 778 put), 웜 586 이벤트(584 get 중 1 miss).

**미룬 이유**: cacheprog는 디스크 캐시 앞에 끼는 필터가 아니라 **디스크 캐시를 완전히 대체**합니다. 기록만 하려 해도 저장소를 직접 구현하고 `DiskPath`를 돌려줘야 합니다. 게다가 내 프로세스가 빌드의 크리티컬 패스에 올라갑니다. 순진한 구현은 Windows에서 get당 3ms를 더했습니다.

**한계**: 프로토콜은 불투명한 해시만 전달합니다. 왜 miss인지 알려주지 않습니다. 다만 ActionID 변환으로 오프라인 귀속은 가능합니다. 콜드에서 get의 약 50%, 웜에서 약 67%는 서브키라 패키지 귀속이 불가능합니다.

**참고할 선행 구현**: `bradfitz/go-tool-cache`의 `cacheproc` 패키지가 재사용 가능한 프로세스 루프를 갖고 있습니다.

### 3.2 `-debug-trace` 소비 · v2

**무엇**: Chrome Trace Event 형식. `B`/`E`/`s`/`f` 네 가지 이벤트. 한 빌드에 13,508 이벤트. 의존성 간 flow 이벤트가 있어 진짜 크리티컬 패스 그래프를 줍니다.

**미룬 이유**: 액션그래프가 대표 질문에 이미 답합니다. 트레이스에는 `ActionID`가 아예 없어서 신원 추적에 쓸 수 없습니다. 둘은 상호보완적이지만 v1에는 중복입니다.

**언제 할 가치가 생기나**: Perfetto 내보내기를 할 때. `ts`가 에포크 기준 마이크로초 float이고 `pid`는 항상 0인 점만 주의하면 됩니다.

### 3.3 HTML 리포트 · v2

**미룬 이유**: 사용자가 v1을 터미널 전용으로 정했습니다. go-size-analyzer(2.2k★)가 HTML로 성공한 전례가 있어 수요는 있습니다.

### 3.4 TUI · v2

**미룬 이유**: pproftui가 6주에 280★를 받은 성공 패턴이지만 v1 범위를 크게 키웁니다.

### 3.5 CI 회귀 게이트 · v2

**무엇**: "지난주 대비 빌드가 40초 느려졌고 범인은 이 의존성"을 PR에 코멘트.

**미룬 이유**: 로컬 진단과 다른 제품에 가깝습니다. 다만 `diff`와 SQLite 이력이 그 토대가 됩니다.

## 4. 보류한 기능

| 기능 | 보류 사유 |
|---|---|
| 원격 캐시 | GOCACHEPROG 구현이 이미 여럿(gobuildcache 105★, cacheprog 58★, tailscale 81★). 전부 얇고 파편화됐지만 이건 캐싱 제품이지 프로파일링 제품이 아님 |
| `go generate` 증분 실행 | 별개 제품. 조사에서 `gogen`으로 따로 후보에 올렸음 |
| CI 테스트 캐시 mtime 복구 | 별개 제품(`gomtime`). Go 이슈 #58571이 Backlog에 있음 |
| 크로스 GOOS/GOARCH 타입체크 | 별개 제품(`gomatrix`) |
| 패키지 여러 개를 한 테스트 바이너리로 링크 | 연구 과제 수준. init 순서, TestMain, 플래그 네임스페이스 문제 |

## 5. 알려진 한계

v1 출시 시점에 README에 적을 내용입니다. 숨기면 신뢰를 잃습니다.

- Go 버전 검사가 PATH의 `go`가 아니라 longpole을 빌드한 툴체인을 봅니다. 보통 같지만 다를 수 있습니다.
- 벽시계를 `go` 프로세스 바깥에서 재므로 액션에 귀속되지 않는 go 명령 기동 시간이 포함됩니다.
- `--explain`은 빌드를 눈에 띄게 느리게 만듭니다.
- `CmdUser` / `CmdSys`는 Windows에서 15.625ms 단위라 쓸 수 없습니다. `CmdReal`만 씁니다.
- `-debug-actiongraph`는 문서화되지 않은 비지원 플래그입니다. Go 1.21~1.27 스키마가 바이트 단위로 동일함을 확인했지만 보장은 없습니다.

## 6. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 비공개 플래그가 바뀜 | 버전 게이트. 테스트 범위 밖은 경고 후 시도. 실패해도 빌드에 영향 없음 |
| `gocachehash`가 바뀜 | 옵트인. 파싱 실패 시 기준선 없는 인과 사슬로 강등 |
| 대형 저장소에서 출력량 폭발 | 스트림 파싱, 문자열 인터닝, 버퍼링 금지. 출시 전 대형 OSS 저장소로 실측 |
| Go가 공식 기능을 내놓음 | 가능성 낮음. #70691이 not-planned로 닫혔고 1.25~1.27에 빌드 관측 기능 추가가 전혀 없었음 |
| 인과 추론이 틀림 | 판정이 아니라 근거 줄이 붙은 사슬로 보고. 데이터가 말하는 것 이상을 주장하지 않음 |

## 7. v1 성공 기준

- 전부 캐시된 빌드에서 "최적화할 것 없음"을 정확히 보고 (경쟁자가 못 하는 것)
- 실제 오픈소스 모노레포에서 크리티컬 패스와 상위 비용 패키지를 찾아내고, 숫자가 전체 벽시계와 들어맞음
- 파일 하나를 고친 뒤 `diff`가 올바른 근원 패키지를 지목
- `--explain` 없이 오버헤드 200ms 미만
- 빌드의 종료 코드와 출력을 절대 바꾸지 않음
